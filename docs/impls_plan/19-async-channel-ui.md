## Goal

Deliverable 10 shipped the Async Channel domain, storage, and the
`AsyncChannelService` REST surface, but **no console screens**. 19 adds them, so
the primary customer-facing resource is manageable from the browser like Agents
and Kafka Clusters already are.

Scope is deliberately **channel CRUD + lifecycle only**: name, `type`,
`channel_partitions`, `labels`, and pause / resume / delete. It follows the
list / register / detail / edit page shape 06 and 08 established — same hooks,
same `updateMask` discipline, same `LabelEditor`, same `confirm()` delete.

**Access-policy UI is out of scope and deferred to
[17](./17-access-policy-and-channel-access.md).** `CreateAsyncChannel` is called
without `access_policy` (an empty policy is a closed channel — zero trust, which
is the correct default), the detail page carries a short non-interactive
placeholder note instead of a policy panel, and no "Clients with access" panel is
rendered because `ListChannelClients` returns `UNIMPLEMENTED` until 17.

## Design

### Routes

| Path | Page |
|---|---|
| `/async-channels` | `ChannelList` |
| `/async-channels/register` | `ChannelRegister` |
| `/async-channels/:name` | `ChannelDetail` |
| `/async-channels/:name/edit` | `ChannelEdit` |

The sidebar's disabled **Async Channels** placeholder becomes a real
`Channels` link; the **Clients** entry stays disabled (deliverable 16 / 17).

### What is editable

`UpdateAsyncChannel` masks **`labels` only** — `type` is immutable,
`channel_partitions` is a staged re-shard (`003.11`), and the access policy has
its own `SetAccessPolicy` RPC. `ChannelEdit` therefore renders type and partition
count as read-only facts and never puts either in a mask.

### Panels deliberately absent from the detail page

| Demo panel | Why it is not here |
|---|---|
| Access policy | deliverable 17 — replaced by a static placeholder note |
| Clients with access | `ListChannelClients` → `UNIMPLEMENTED` until 17 |
| Generated Kafka Topics (table) | shard rows are materialised by placement (ADR-API-009) — replaced by a "0 of N placed" note |
| Placement context | placement coordinates are ordinary `franz.placement/*` labels; the generic `LabelEditor` covers them |
| Discovery / SDK usage | needs a real SDK and a client identity (16 / 17) |

## Done when

- From the browser only: create an Async Channel, see it listed, open its detail
  page, edit its labels, and pause / resume / delete it — every change
  round-trips (reload shows it).
- The edit form never presents `type`, `channel_partitions` or the access policy
  as editable, and never sends one in an `update_mask`.
- No access-policy or client-access UI ships; `CreateAsyncChannel` is called
  without `access_policy`.
- `npm run typecheck` / `lint` / `test` / `build` and the Playwright smoke are
  green.

## Notes

- **Numbering** — 19 is the next free deliverable number (01–18 exist). The plan
  has no separate convention for a UI-only follow-up: deliverable 08 set the
  precedent that console work is its own numbered deliverable rather than an
  amendment to the backend one, so 19 follows it.
- The list page does not paginate. `ListAsyncChannels` supports
  `page.pageSize` / `page.pageToken`, but no console list paginates yet;
  adding it to one screen only would be inconsistent. Worth a separate
  deliverable across all four list pages.
- The detail page does **not** poll. Unlike a Kafka Cluster (whose provider
  status trends toward `READY` on its own), nothing about a channel changes
  server-side without an operator action, so a 4s poll would be pure noise.
  When placement (13) starts materialising shards, the shard panel will want one.
- `channelStateLabel` exists for prose contexts; the pills themselves go through
  the shared `StatusPill`, which already renders `CHANNEL_STATE_*` correctly
  (`ACTIVE` → neutral, `PAUSED` → paused, `DELETED` → error).
