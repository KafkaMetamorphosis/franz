## Goal

Deliverables 14 and 15 shipped the Indicator registry, the Policy engine, and
live current-value/health maintenance — but **no console screens**. Today the
only way to register an indicator, author a policy, or see a `PolicyAction`
audit trail is a raw API call. 20 adds the screens, following the list /
register / detail / edit shape 06, 08, and 19 established.

This closes a real gap, not a nice-to-have: without it, Governance is
effectively an API-only feature with no operator surface, which was flagged
while reviewing 15's "is it possible to see indicators in the UI?" — the
answer was no, and no existing deliverable scoped one.

**Two resources, one deliverable** — Indicators and Policies are governed
together in `003.8` and a Policy is unauthorable without picking a registered
Indicator, so splitting them across two deliverables would leave one
half-useful without the other.

## Design

### Routes

| Path | Page |
|---|---|
| `/governance/indicators` | `IndicatorList` |
| `/governance/indicators/register` | `IndicatorRegister` |
| `/governance/indicators/:name` | `IndicatorDetail` |
| `/governance/indicators/:name/edit` | `IndicatorEdit` |
| `/governance/policies` | `PolicyList` |
| `/governance/policies/register` | `PolicyRegister` |
| `/governance/policies/:name` | `PolicyDetail` |
| `/governance/policies/:name/edit` | `PolicyEdit` |

Sidebar gains a **Governance** section with two links (Indicators, Policies),
mirroring how Agents / Kafka Clusters sit side by side today.

### What is editable

- **Indicator**: `UpdateIndicator` masks `unit`, `staleness_threshold`,
  `source_agents` — `applies_to` is immutable (`003.14`) and `IndicatorEdit`
  never puts it in a mask. `current_value` / `health` / `last_sample_at` are
  read-only projections, never form fields.
- **Policy**: `UpdatePolicy` masks `matcher`, `limit`, `actions`, `weight`,
  `enabled` — `indicator` is immutable (changing it would silently
  reinterpret an existing Limit's value against a different unit).
  `PolicyRegister`/`PolicyEdit` render server-side whitelist-violation errors
  (`003.8`'s `(entity, field, ops)` matrix) inline on the offending action row
  rather than as a generic toast — the whole point of surfacing this in the
  UI is to make an invalid policy *legible* before Create/Update rejects it.

### Panels

| Panel | Where | Source |
|---|---|---|
| Recent samples (table, not a chart) | `IndicatorDetail` | `ListIndicatorSamples` |
| Recent `PolicyAction`s (audit log) | `PolicyDetail` | `ListPolicyActions` |
| Dry-run | `PolicyDetail` | `DryRunPolicy` — an inline form (resource FRN + a hypothetical value) that renders the actions *that would* fire, with a visible "not applied" note; no mutation |

### Deliberately deferred

| Item | Why not here |
|---|---|
| A real sparkline/chart on `IndicatorDetail` | a table of recent samples answers "is this healthy" well enough; charting is a separate, larger UI investment worth its own pass across the console (topic/cluster metrics too) |
| Cross-linking an Indicator's health onto the `KafkaTopic`/`KafkaCluster` detail pages it applies to | needs a "which indicators apply to this resource" query `GovernanceService` does not expose yet; do it if/when Governance grows a reverse lookup |
| List pagination | no console list paginates yet (`003.11`'s open item, restated in 19's Notes) — still one deliverable's worth of work across every list page at once |

## Done when

- From the browser only: register an Indicator, see it listed, open its
  detail page (current value / health once a sample lands), edit its
  staleness threshold, and delete it (blocked with a clear message if a
  Policy still references it).
- From the browser only: register a Policy against a registered Indicator,
  see it listed, dry-run it against a hypothetical value with no mutation,
  and see its `PolicyAction` audit trail after a real evaluation fires one.
- Neither edit form ever presents an immutable field (`Indicator.applies_to`,
  `Policy.indicator`) as editable, and neither ever sends one in an
  `update_mask`.
- A whitelist-violation (`003.8`'s matrix) or unknown-indicator rejection from
  `CreatePolicy`/`UpdatePolicy` renders as a specific, actionable message, not
  a raw gRPC status string.
- `npm run typecheck` / `lint` / `test` / `build` and the Playwright smoke are
  green.

## Notes

- **Numbering** — 20 is the next free deliverable number (01–19 exist,
  including the swap that produced today's 14/15). Same precedent 08 and 19
  set: console work for an already-shipped backend is its own numbered
  deliverable, not an amendment to 14/15.
- **Why this wasn't scoped earlier**: 14's and 15's plans were written and
  executed backend-first (`GovernanceService`/`TelemetryService` only); no
  deliverable's task list ever mentioned a console page for either, so the gap
  went unnoticed until it was asked about directly after 15 shipped. Worth
  remembering when scoping a future backend-only deliverable: name the UI
  follow-up in the plan at the same time, even if it's a stub entry, so it
  doesn't have to be discovered later.
- **Local dev prerequisite**: `local/seed/04-indicators.sql` (added alongside
  this deliverable's scoping) registers the 13 indicators Gregor Samsa
  publishes, so `IndicatorList` has real rows and real current-value/health
  data to render against the local loop without hand-authoring a `CreateIndicator`
  call first.
- No production/multi-realm equivalent of that seed exists yet — a real
  deployment still needs its own provisioning step to register the indicators
  its agents publish before their samples stop 404ing as
  `FAILED_PRECONDITION`. Out of scope for a console-only deliverable; tracked
  in `docs/impls_tracker/15-telemetry-ingest.md`.
